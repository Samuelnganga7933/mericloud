Process

What working with us is actually like.

Five stages, each ending with something concrete that you approve before the next begins.

1Discovery

We learn how the work is done today and define the problem.

2Architecture

We design how the system will work, before building it.

3Development

We build in short releases, each one a working piece.

4Deployment

We put it live and make sure it is ready for real use.

5Ongoing support

We keep it healthy and improve it as the business changes.

Stage 1 of 5

Discovery

We talk to the people who run the process, look at the tools and documents involved and follow real examples from start to finish.

A team talking through the problem.
Why it matters

Many failed projects solve the wrong problem. Discovery is where the problem gets defined while changing it is still cheap.

What we do
  • Hold conversations with the people who use the system
  • Map the current workflow, step by step
  • Review existing systems, data and accounts
  • Note constraints: budget, deadlines, compliance, staff skills
What you contribute
  • Give us access to people and real examples
  • Tell us what matters most
  • Share the tools and documents in use
Decisions made here
  • Which problem is being solved
  • What the first release must do
  • What is out of scope for now
What you receive
  • Written problem definition
  • Map of the current process
  • Requirements in priority order
  • Risks and open questions
BEFORE MOVING FORWARD

You approve the problem definition and priorities before any design work begins.

Stage 2 of 5

Architecture

We design the parts of the system, the data it holds, what it connects to and where it will run.

A monitoring view that shapes the design.
Why it matters

Choices made here set the cost, speed and security of the system, and how easily it can change later.

What we do
  • Draw the system and the data model
  • Choose technologies and explain the trade-offs
  • Plan integrations with payments, couriers, accounting and other tools
  • Plan hosting, security and backups
  • Split the build into releases with estimates
What you contribute
  • Review the design in plain language
  • Provide access to the accounts we must integrate with
  • Choose between the options we present
Decisions made here
  • Technology and hosting
  • What to build, buy or integrate
  • The order of releases
What you receive
  • System diagram
  • Data model
  • Integration plan
  • Security and hosting plan
  • Release plan with estimates
BEFORE MOVING FORWARD

You see the design and the estimate, and agree the plan or change it.

Stage 3 of 5

Development

We build the system in short cycles. Each release is a working piece you can try on a staging site.

A workflow built and tested step by step.
Why it matters

Seeing real software early is the quickest way to find what we misunderstood.

What we do
  • Implement the features in the plan
  • Write automated tests for the parts that matter
  • Review each other's code
  • Deploy every release to a staging site
  • Collect your feedback and act on it
What you contribute
  • Try each release with real examples
  • Give feedback while it is fresh
  • Decide when questions arise
Decisions made here
  • Adjustments to features
  • What moves to a later release
What you receive
  • Working releases on a staging site
  • Automated tests
  • Release notes
  • Updated documentation
BEFORE MOVING FORWARD

You accept each release before the next one is built on top of it.

Stage 4 of 5

Deployment

We move the system into production and prepare the people and infrastructure around it.

A server room where deployments run.
Why it matters

A system that worked in testing can still fail on launch day if nobody rehearsed it.

What we do
  • Configure production hosting, security and monitoring
  • Migrate existing data where needed
  • Rehearse the release and a way back
  • Train your team
  • Hand over code, accounts and documentation
What you contribute
  • Make staff available for training
  • Approve go-live
  • Provide final data and account details
Decisions made here
  • Launch date and cut-over method
  • Who owns which accounts
What you receive
  • Live system with monitoring and backups
  • Migrated data, where applicable
  • Handover documentation
  • Staff training session
BEFORE MOVING FORWARD

A go-live checklist is signed off, including backups and a tested way back.

Stage 5 of 5

Ongoing support

We look after the system after launch and change it as the business changes.

Maintenance work done before trouble starts.
Why it matters

Software that is not maintained slowly breaks: updates pile up, integrations change and security gaps open.

What we do
  • Monitor availability and errors
  • Fix faults
  • Apply security and dependency updates
  • Make small improvements
  • Review performance and plan larger changes
What you contribute
  • Report issues as they appear
  • Tell us when the business changes
  • Join a periodic review
Decisions made here
  • Priorities for improvement
  • When to extend or retire parts of the system
What you receive
  • Monitoring and alert response
  • Maintenance releases
  • Periodic review
  • An improvement backlog
BEFORE MOVING FORWARD

Scope, response expectations and contact route are agreed before launch.

How we communicate

You have one named contact. Progress is reported in writing at an agreed interval, every release is demonstrated, and decisions are recorded so nobody has to remember what was agreed.

Milestones

Each stage ends with a review. Work does not start on the next stage until you have accepted the last one, so you can stop, pause or change direction at a known point.

When requirements change

They usually do. A change is described, we explain what it does to scope, effort and order of work, and you decide: include it now, schedule it later or drop it.
